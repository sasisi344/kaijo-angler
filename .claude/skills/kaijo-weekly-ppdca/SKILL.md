# kaijo-angler 週報PPDCA（アクセスデータ → next-task / weekly-task）

データの置き場・期間ルールの正本は `.workspace/.task/access-data/CLAUDE.md` と `INDEX.md`。**ここを先に読み、期間の違うデータを直接比較しない**。

## PPDCA の各フェーズ

PDCA に「問題の把握」を加えた 5 段階（統計の PPDAC に相当）。

| フェーズ | 意味 | このスキルでやること | 成果物 |
|---|---|---|---|
| **P**roblem | 問題の把握・明確化・予知 | 最新 wNN の配置確認・INDEX 登録・比較モード決定 → データ分析 → 問題の抽出と明確化（手順1〜2） | 問題リスト（数値つき） |
| **P**lan | 仮説の設定・実践の計画 | 問題ごとに仮説を立て、優先度判定・起票（手順3〜4） | `next-task` / `weekly-task` / [[measurement-task]] |
| **D**o | 実行・データ収集 | `next-task` を実行（別セッションで可）。効果測定用データの収集 | 変更・コミット |
| **C**heck | 評価・データに基づく分析 | 次週以降のデータで仮説を検証（[[measurement-task]] の判定） | 検証結果 |
| **A**ction | 改善・結論 | 採否判断・横展開・次週タスク化。完了は archive へ | 結論・新タスク |

本スキルの守備範囲は **Problem〜Plan（起票まで）**。Do は起票後に着手。Check/Action は次週の本スキル実行時に[[measurement-task]]を見て行い、その結果を次サイクルの Problem に引き継ぐ。**ユーザーが明示するまで記事の編集・コミット・画像生成は行わない。**

## 手順

### 1. Problem①：データと比較モードの確認

1. `access-data/CLAUDE.md` → `INDEX.md` を読む。対象 wNN の行がなければ、フォルダの CSV からヘッダー日付・総計を読んで **INDEX.md に行を追加**（CLAUDE.md の更新手順どおり）。GSC の実期間が不明なら「推定」と明記しユーザーに確認を依頼
2. INDEX の「前週比較」列で比較モードを決める

   | モード | 条件 | 使い方 |
   |---|---|---|
   | **A: WoW** | GSC 7日 × 7日（w42 以降は常にこれ） | 前週比（クリック・表示回数・CTR・順位）を出す |
   | **B: ベースライン比較** | 今週 GSC=7日・前回=3か月（w41 のみ） | WoW は出さない。w40 の3か月値を÷13した週平均と並べ「平常範囲か」だけ見る |
   | **GA4 のみ** | 期間日数が違う | セッション÷日数の日平均で比較 |

3. 前週が欠番（w38・w39 のように）なら無理に埋めず、「比較不能」と書いて今週の絶対値と異常検知で進める

### 2. Problem②：分析して問題を明確化する（この順で見る）

結果は「何が・どの数値で・何と比べて問題か」を 1 行で言える形にする（例: 「w41 `sendai-port-central-park-sea-square` 表示179・順位10.8・CTR2.8%＝順位の割にCTR低」）。原因の推測は Plan の仮説に回す。

- **サイト全体**: GA4 セッション（日平均）・エンゲージメント率・キーイベント。GSC クリック・表示回数・平均CTR（サイト平均CTRは 4.6% 前後で安定。**タイトルの一括改善は不要** → 個別ピンポイントのみ）
- **ページ別（GSC ページ CSV）**: slug 単位で新旧URL（`/blog/<slug>/` ↔ `/fishing-facility/<slug>/` 等）を合算。`/blog/intelligence/` は現行URLなので合算しない
  - 表示回数が閾値（ページ50以上）を超え、①CTR が極端に低い ②順位 8〜20 で伸び代がある ③前週比で急落／急騰 を抽出
- **クエリ別**: 表示回数20以上のみ。単週は急騰ワード（新規需要・記事化候補）と施設名クエリの異常だけ見る。判定は**直近4週合算**
- **技術**: GA4 の LP に 404 系タイトル・旧URLが出ていないか／GSC のページに旧URL側が増えていないか（[[measurement-task]] M4）
- **収益**: `affiliatecard_click` と `gothere_click`（イベント名ごとの行。**セッションはイベント名で足さない**）。`affiliate_id`・`placement`・`facility_id` は登録日以降のみ有効。[[measurement-task]] M1・M6 の判定材料を更新
- **地域**: w41 以降の GA4 は市区町村あり → GoThere の出発地・アクセスガイドの需要地の確認材料に使う
- スクリプト: `scripts/analyze-facility-ranking.mjs`（既定パスが古いので**引数で CSV パスを渡す**）、`analyze-query-mix.mjs`、`analyze-region-density.mjs`。集計は Python/Node で行ってよい（CSV は UTF-8、ページ名・クエリは日本語）

### 3. Plan①：仮説と優先度判定

各問題に **仮説**（原因の見立てと、直すと何がどう変わるか。例: 「施設名クエリでマップ枠にクリックを奪われている」「旧URL側に評価が残っている」）を 1〜2 文で立てる。仮説が立たない問題は、まず原因調査を next-task / weekly-task の最初の作業にする。続けて各課題に **カテゴリ**（SEO技術／SEO-CTR・順位／物販／観光導線／コンテンツ／計測）と **工数**（S=30分以内／M=1セッション／L=複数セッション）を付け、次の基準で振り分ける。

#### → `next-task.md`（すぐ解決するべき）に入れる条件（いずれか1つ）

| # | 条件 | 例 |
|---|---|---|
| N1 | **流入を失っている技術障害**: 404・リダイレクト不備・noindex・canonical誤り・インデックス欠落・旧URL側へ逆流 | 旧URLが伸びている施設、GA4 に 404 LP |
| N2 | **急落**: 表示回数≥50 のページで前週比クリック -30% 以上（WoW 可能な週のみ） | 順位が突然10位以上落ちた施設 |
| N3 | **他の作業・効果測定のブロッカー**: これを終えないと他施策が進まない／測定が汚れる | インデックス登録リクエスト、計測欠損 |
| N4 | **収益に直結する不具合**: アフィリエイトの誤対応・リンク切れ・`tag=`漏れ・クリック計測の欠落 | `affiliatecard_click` が0の面 |
| N5 | **工数S かつ効果が明確**: 表示≥50・順位≤10 なのにCTR<2% のページ1本のタイトル/メタ調整など | ピンポイントのCTR改善 |

- 上限は**同時5件**。超えたら N1→N4→N3→N2→N5 の順に残し、あふれた分は weekly-task へ回す
- 完了条件を1行で書く（「GSC で〜が確認できる」ではなく、実行側が判断できる条件）

#### → `weekly-task.md`（後回し・セッションに余裕があれば）に入れる条件

- 施策の効果が中長期で出るもの: 新規記事・大型リライト・内部リンク網の拡張・横展開（新地域のハブ化 等）
- 表示回数が閾値未満で判断が不確かなもの（4週合算を待つ）
- 工数 L で緊急性がないもの、任意の改善・スクリプト改修
- 優先度は **Tier2（今月中に着手したい）／Tier3（任意）** に分ける。Tier1 は使わない（すぐやるものは next-task）
- 各タスクに**昇格条件**を1行書く（例: 「4週合算で表示≥100 かつ順位≤10 なら next-task へ」「`gothere_click` が週10件超なら昇格」）
- **4週間更新されない項目**は、残す根拠を見直して削除または archive へ移す

#### → どちらでもない

- データが将来揃わないと判定できない → [[measurement-task]] に追記（測定対象・必要データ・判定基準・取得タイミング）
- GSC 管理画面の手動作業（URL検査・インデックス登録・再インデックス） → [[subtask]] に URL リスト化
- 完了済みの実行ログ → `.workspace/archive/task/` へ

#### 迷ったときの方針

- **物販（アフィリエイト）強化を当面重視**（2026-09-30方針）。SEO-CTR改善より物販の不具合・導線の穴を優先
- 「釣り堀」一般語・全国網羅の弱さといった**構造課題**は単発タスクにせず、診断型ハブ（[[diagnosis-app-task]]）側で扱う
- 平均CTR起因の一括タイトル書き換えは起票しない

### 4. Plan②：起票（書き込み）

1. `next-task.md`・`weekly-task.md`・[[measurement-task]] を**先に読み、既存項目と重複しないか確認**。重複は既存項目に今週の根拠を追記する
2. 書式（既存ファイルの体裁に合わせる）

   ```markdown
   - [ ] **<タスク名>（wNN・<カテゴリ>・工数S/M/L）**
     - 問題: <指標・値・期間。例: w41 GSC 7日、表示137・CTR13.9%・順位5.6>
     - 仮説: <原因の見立てと期待する変化>
     - 対象: <slug / URL>
     - やること: <具体作業>
     - 完了条件: <Do の完了を判断できる条件>
     - 検証（Check）: <何を・いつ・どの値で見るか。データ待ちなら [[measurement-task]] M? へ登録>
     - 昇格条件: <weekly のみ>
   ```

   `next-task` は Do の入口、検証欄が Check の入口になる。検証欄を空にしない（効果が測れない施策は起票しない）。

3. **初回実行時のみ**: 既存の `next-task.md`・`weekly-task.md` の項目を上の基準で再分類する（現状は next-task=「次に控えているタスク」、weekly=Tier1〜3で定義が違う）。大きく動かす前にユーザーへ移動案を提示して合意を取る
4. ファイル冒頭に「最終更新 wNN（日付）」を書く。完了したタスクは [x] にして archive へ移す

### 5. 終了時の報告

次の4点を短くまとめる:
- 使ったデータと比較モード（例: 「w41 GSC 7日、前週が3か月なので WoW 不可、w40÷13 と比較」）
- 主な問題（3〜5点、数値つき）と、前サイクルの Check/Action の結果（[[measurement-task]] で判定できたもの）
- 起票した next-task / weekly-task の件数と、**next-task に入れた理由**（N1〜N5）
- データ不足・要確認事項（GSC 実期間、欠番週 等）

## ガードレール

- 期間の異なる GSC 絶対値を直接比較しない（w40 3か月 vs w41 7日 の増減を「悪化」と報告しない）
- 7日データのクエリ単位の順位・CTR で施策判断しない（4週合算を待つ）
- `/blog/` の一括処理系の変更は `intelligence`（現行 `/blog/intelligence/`）を除外する
- 施設記事の `slug:` は URL を決める必須項目。タスク化するときに「slug 不要」としない
- アフィリエイトは AffiliateCard / TackleCard / GoThere 経由（[[kaijo-ui-components]] スキル参照）。管理は `.workspace/affiliate-tags/物販/`
- 記事本文の強調は `<strong>`（`**` 不可）。MDX import は `~/`
- GSC/GA4 の手動作業が必要なものは、実施可能な形（URL リスト・手順）で subtask に書く
