# KA-PORTAL-09 休業告知の更新運用（CC 案・ユーザーの決定待ち）

作成: 2026-11-21（CC）／関連: `.workspace/.task/next-task.md` 項目9 の順6、`schedule-task.md` M12 の「運用点検」、冬の営業台帳 `.data-set/winter-facility-status.md`（項目6）

## 前提（今の仕組み）

- 期間のある休業は施設記事の `facility_details.seasonal_closures`（from／to／reopen／reason／source_url／verified_at）。閉業・再開未定は `status`。今 `seasonal_closures` を持つ施設は12
- `/api/facilities.json` はビルド時に作る（`prerender = true`）。**期間そのもの**を渡しているので、期間の始まり・終わりの判定はブラウザーが日付で行い、再ビルドは要らない
- 再ビルドが要るのは、**新しい告知・期間の変更・閉業**を記事に入れたとき。ここを人が回す

## 案

| 項目 | 案 |
|---|---|
| 担当 | CC（公式の確認・記事と台帳の修正・ビルド・公開 JSON の確認）。電話でしか分からない施設だけユーザー |
| 扱う範囲 | 冬季休業・長期の休止・閉業。1〜数日の臨時休業・定休日は扱わない（記事と検索は「公式で確かめる」へ送る） |
| 定期の確認 | 11〜3月は月2回（1日・15日ごろ）、4〜10月は月1回。対象は `seasonal_closures` のある施設と、台帳で「要確認」の施設。hq の daily に載せる |
| 期日の確認 | `from` の14日前と、`to`（または `reopen`）の7日前に、公式の告知が変わっていないかを見る |
| 臨時のきっかけ | 公式 SNS・ユーザー・読者からの情報、GSC で施設名＋「休業」「閉業」が出たとき |
| 春の確認 | 4月に、翌冬の告知が出ていないか（出ていなければ何も入れない） |

### 更新の流れ（1件ずつ同じ手順）

1. 公式で確認する（告知の URL を控える）。過去の年の告知を今季に読み替えない。告知がなければ日付を入れず、台帳は「要確認」のまま
2. 施設記事を直す: `seasonal_closures` か `status`、本文の休業の記述、`verified_at`
3. 台帳 `.data-set/winter-facility-status.md` の行を直す
4. 同じ施設が出るまとめ・ランキング・トップを `grep` で探し、施設記事に合わせる（数値の正本は施設記事。2026-11-15 ユーザー決定）
5. ビルド → main へ → deploy
6. 本番の `/api/facilities.json` で、その施設の期間が新しい値になっていることを確かめる。結果を `.workspace/.task/` の記録に1行残す

## ユーザーに決めてほしいこと

1. **頻度**: 上の案（冬は月2回・それ以外は月1回）でよいか
2. **deploy の承認**: 休業情報だけの更新（上の 2〜4 の範囲）は、表を見せずに main へ入れてよいか（包括承認）。今のルールでは `src/` が変わるので毎回承認が要る。冬は告知が続くので、承認待ちの間に古い表示が残る
3. **電話確認**: 公式に告知がない施設を、電話で確かめるか、「要確認」のまま置くか（項目6・06 の電話確認と同じ判断）

## 道具（決まったら CC が作る、規模 S）

- `seasonal_closures` の `from`／`to` が近い施設（14日以内）を一覧にするスクリプト。定期の確認のときに回す
